# Ground-truth parser test (run 2026-10-22)

Code and data in this folder: `text/` (ground truth), `scripts/` (fetch, four generators, extract, score), `scores.json`. The 85 PDFs are regenerated by the scripts (Chrome, Typst, PyMuPDF and Word must be installed). Same parser versions as the app (pypdf 6.20.1, PyMuPDF 1.28.2, pdfplumber 0.11.10, PyMuPDF4LLM 1.28.2).

## Setup
- **Text:** the opening ~2,200–3,600 characters of the Wikipedia article "India" in 17 languages (Arabic, Bengali, Chinese, English, Gujarati, Hindi, Japanese, Kannada, Korean, Malayalam, Marathi, Punjabi, Russian, Tamil, Telugu, Thai, Urdu), fetched as plain text via the MediaWiki API, NFC-normalised. This is the ground truth.
- **PDFs:** each text turned into a PDF by 5 generators: Chrome print-to-PDF (plain, and with every 4th word an underlined link), Typst 0.15, PyMuPDF Story (MuPDF's writer), Microsoft Word "Save as PDF". System fonts (Nirmala UI for Indic scripts, Arial, Leelawadee UI, YaHei, Yu Gothic, Malgun Gothic, Calibri). 85 PDFs; page 1 of every suspicious file was rendered and checked by eye: all text displays correctly.
- **Measure:** 20 random 12-character snippets of the ground truth (whitespace removed) searched in each parser's output (whitespace removed). "Hit" = share found. Also: Levenshtein similarity, repeated combining marks, broken characters (control/private-use/U+FFFD).
- 5 parser setups × 85 PDFs = 425 comparisons, 0 crashes.

## The generator matters as much as the parser
Same Hindi paragraph, same parser (PyMuPDF): Chrome 0.95 · Typst 1.00 · **Word 0.15 · MuPDF 0.10**. On Word- and MuPDF-made files **every parser returns the same wrong text** ("आधिकाररक" for "आधिकारिक"; "गणराăय"): the PDF's own glyph-to-character map is wrong. The same holds for all nine Indic scripts tested and for Arabic. These files render perfectly; nothing but a human (or OCR) can tell.

Typst files: pypdf and pdfplumber emit control codes between letters in every Indic script (hit 0.00); PyMuPDF reads them cleanly.

## Hypothesis rejected
The repeated vowel signs are **not** caused by underlined links: the Chrome file with links has exactly the same 44 repeats as the one without.

## What the app can and cannot detect (as of this run)
- Detects: broken characters, repeated marks (new check, 0 false positives on 17 ground-truth texts and the Lewis/Barnett outputs), look-alike/presentation forms, reading-order disagreement between libraries, word-count collapse, (cid:NN).
- Partly detects a wrong character map that every parser reads the same way: on the Word Hindi/Gujarati files the repeated-mark check fires for all six setups (9 and 33 repeats), which is itself the signal that the file, not a parser, is at fault. Where the wrong map produces valid-looking text (MuPDF Hindi "गणराăय"), nothing fires. The app now says so under the findings and tells the visitor to search for a sentence from the page.
- Stress harness on 15 of these PDFs (11 languages, 5 generators): 15 OK, 0 bugs, 3–8 s each. Full 31-file corpus re-run: 0 bugs, 12 rejections, 19 OK, same as before; the new check fires on wiki_hindi (156, PyMuPDF) and the Gazette (3, all six setups) only.
- Deployed to the Space 2026-10-22 (commit 8d2becd); live checks passed: injection file, Hindi (17 s), renamed PNG rejected, and four generated PDFs (Arabic/Word, Thai/Typst, Gujarati/Word, English with links) showed the new findings, 4–8 s each.
- Known verbosity: on Thai (no spaces between words) the "fewer words" message fires for several parsers at once because word counts are meaningless there.

## Caveats
- One paragraph per language, one font per script, five generators; LaTeX/arXiv files were covered separately (Lewis, Barnett). Not a benchmark.
- Hit rate counts findability of 12-character snippets, so a parser can score high while still damaging some words (PyMuPDF on Hindi: 0.95 with 44 repeated marks).
- Levenshtein similarity is not meaningful for right-to-left output and is reported only in `scores.json`.
